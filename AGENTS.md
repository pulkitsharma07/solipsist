# Solipsist: notes for coding agents

How the code is laid out, the words it uses and the rules it keeps. Read it before changing anything.

Writing app: a Tiptap editor on the `.md` files of the folder it runs in. The first launch shows the files `md_search_paths` finds (globs, default `*.md`); the ones picked are copied to `.solipsist/pages/<path>.md`, worked on there, and written back only by Sync (`src/server/project.ts`). Under `bun test` only, `DOCS_DIR` makes that folder the pages themselves: no dialog, no Sync; elsewhere it is ignored. Comments live in a hidden HTML block at the end of the working copy. No database.

## Glossary

The words, in code, comments and docs. "Placeholder" used to mean all of the first three.

| Term | Means | Code |
|---|---|---|
| **task** | one thing the writer asked for; it has an id, a state and an agent | `TaskRecord`, `TaskState`, `TaskAgent`, `newTaskId`, `ackTask` |
| **marker** | a task's comment in the text: a point or a range | `markerComments`, `markersIn`, `MarkerPoint`, `MarkerRange` |
| **task type** | what a task does (`gen`, `sel`, `img`), defined by a plugin | `TaskTypePlugin`, `taskType` |
| **state** | pending, working, suggested, done; on disk `ack`, `sug` | `TaskState` |
| **suggestion** | the agent's result for a task, waiting for the writer to decide | `suggestion*`, `pruneSuggestions` |
| **task record** | what is stored about a task in the hidden block | `TaskRecord` |
| **task agent** | the agent working on a task | `TaskAgent` |

What is saved, sent or shown uses these words too: the hidden block's `tasks`, a record's `type` and `suggestion`, the Tiptap
names `markerPoint` / `markerRange` and their `taskType` attribute, the CSS classes (`task-*`), the routes (`/api/pages/…`),
the prompt ids (`type.<type>`). Until the first release there are no aliases and no old names kept for compatibility:
rename outright, and don't add a fallback for something saved under an old name.
`test/vocabulary.test.ts` fails on a new `Placeholder*` type or function name outside `dialect/`.

## Commands

- `bun run dev` serves on `PORT` (`.env`, see `.env.example`). `bun test` runs everything, no network. `bun run typecheck` (`bun --bun tsc`; plain `tsc` fails on the system Node) also runs inside `bun test`.
- `bun run features` rewrites `FEATURES.html` (see Rules).
- `site/`: the website, an Astro Starlight project with its own `package.json` (`cd site && bun install`; `bun run dev`, `bun run build` to `site/dist/`, which `.github/workflows/pages.yml` publishes). The landing page is served at `/`, the documentation at `/docs/` (`site/src/content/docs/docs/`, Markdown). `scripts/site/build.ts` (`bun run site`, run first by the site's `dev` and `build`) generates `site/src/landing.html` from `scripts/site/template.html`, the docs' configuration page from `CONFIGURATION.md`, and copies `FEATURES.html` to `/features.html`; all three are git-ignored. A change to what the app does that the docs describe (keys, settings, the cards, buttons, chat) changes its page there too. The docs' pictures (`<Shot name=…>`, `site/src/components/Shot.astro`, light and dark) are drawn by `bun run site:shots` (`scripts/site/shots.ts`: real Chrome photographing FEATURES.html's specimens and the landing page's diagram) into `site/src/assets/shots/`, committed: run it after `bun run features` when a pictured part changes.
- CI (`.github/workflows/`): `ci.yml` runs `bun test`, then `bun run test:ui`, on Linux only (no macOS runners while the repo is private: they cost ten times as much). The UI job is on `ubuntu-24.04`, which Playwright 1.56 can install its browser for; `ubuntu-latest` is 26.04. `fuzz.yml` runs the long fuzz nightly; `repeat.yml` runs one suite N times, to catch a flaky test. No Dependabot: dependencies are upgraded by hand (see Rules).
- Settings: `solipsist.yaml` (found by `--config`, `./`, `~/.config/solipsist/`), overridden by env vars; `CONFIGURATION.md` (public: its top is hand-written, the reference below `config:start` generated) lists them all, `bun src/index.ts --print-config` shows what is in effect, and the gear's Loaded settings tab shows it in the browser. They are rows of one table (`src/server/config/table.ts`, the rows in `config/*Rows.ts`, the types in `src/server/config.ts`); after changing it run `bun scripts/config-docs.ts` (a test fails while `CONFIGURATION.md` or `solipsist.example.yaml` is stale). `test/setup.ts` (a bunfig preload) keeps a developer's own files, folders and keys out of every test (see Rules).
- `test/fuzz.test.ts`: random pages and edit runs; a failure prints its seed and a shrunk case, which becomes a named test. `FUZZ_RUNS=16000 bun test test/fuzz.test.ts` searches longer; run it after a change to the dialect, the merge or the session.
- `test/e2e-dom/` (part of `bun test`, no browser): the real server in-process (`src/server/routes.ts`) and the real app in happy-dom over real HTTP, with a scripted model (`app.tsx`: `ScriptedEngine`, `Gate` to hold a run). Suites `*.dom.tsx`, run in their own process by `test/e2e-dom.test.ts` (other files mock `client.ts` process-wide); one alone: `bun test ./test/e2e-dom/agent.dom.tsx`. Every suite imports `./platform` first: the suites play a Mac, and ProseMirror's keymap decides what `Mod` means when it loads, before happy-dom is registered. `page` (saving, changes arriving, tabs), `agent` (asks, decisions, races), `chat`, `chat-stream` (every kind of reply, on the fake agent of `test/chat-harness/agent.ts`), `pi` (the real Pi engine on a scripted model, `test/e2e/pi-script.ts`), `settings`, `review`, `fuzz` (random sessions; `DOM_FUZZ_SEEDS`, `DOM_FUZZ_RUNS`, `DOM_FUZZ_LOG=1`).
- `bun run test:ui`: real Chrome via Playwright (`E2E_CHANNEL` picks another), not part of `bun test`, only for what a fake DOM can't show (real typing, layout, the pointer, scrolling, the clipboard); a test of what the app does goes in `test/e2e-dom/`. Run it after a change to the page's layout or the editor's input. Three suites: `smoke.e2e.ts` (dev server on a scratch `DOCS_DIR`, fake agent), `chat.e2e.ts` (how the chat's log scrolls, against `test/chat-harness/server.ts`, a fake agent that streams every kind of reply by a word in the message: `tool`, `tools`, `long`, `think`, `code`, `slow`, `suggest`, `reply` (our own tools), `bad`, `error`, `decline`; serve it by hand with `bun test/chat-harness/server.ts`, `?ph=long` / `?ph=gone`), `pi.e2e.ts` (Page review in the margin: the real server with Pi on a scripted model, `pi-server.ts`, answering by task id: it and the smoke suite's fake match the run prompt's "the gen task abc," and the chat's "about task abc"). `leftovers.ts` writes down every browser and server a suite starts, so a run that is killed leaves nothing behind. `E2E_VIDEO=<dir>` records each page (`bun --bun node_modules/playwright/cli.js install ffmpeg`).
- `monke/` (git-ignored for now, so not in a clone): a monkey tester that uses the app the way a person would for N minutes, on real models through OpenRouter, and records it. A project of its own (`cd monke && bun install`, `bun run monke`, its own `bun test`); its `README.md` says how to run it and what each run leaves in `monke-runs/`. Not part of `bun test` or CI, and it spends money: run it only when asked.

## Map

- `src/shared/docfile/`: file format, markdown <-> doc (used by browser and server).
  - The page format is `FORMAT` (`file.ts`), written first in the block on every write. Raise it only for a change an older build would get wrong (a new key needs none: every build keeps keys it doesn't know, `extra`); add `test/fixtures/format-<n>/` when you do. A page in a newer format is never written (`NewerPageError`, 423 from every route; Sync too), its agents are off, and the app shows it read-only (`NewerPage.tsx`). `test/format.test.tsx`.
  - 3-way `mergeBodies` is a tree merge (`treeMerge.ts`: blocks, list items, rows, cells); a text block changed on both sides conflicts unless their side only finished a task in it. Also diffs.
  - Markers are comments of a registered task type, states pending/ack/sug/done/btn (`:btn`: a result kept as a button, below): one point node `markerPoint`, one range mark `markerRange` (`POINT_NODE`, `RANGE_MARK`; `MarkerPoint`, `MarkerRange` in code), both with a `taskType` attribute. A task type with `instruction` keeps the writer's words on the opening comment, `<!-- sel:abc "make it shorter" -->` (escaped, as hex in the stand-in). A range around anything that isn't text (an image, a point marker) has its comments written by the dialect (`nodeRangesToText`): Tiptap writes a mark's markdown around text only.
  - `suggestions.ts`: `decide` = accept, reject, ask again or accept as a button on a `:sug` marker, from its record, as steps on the writer's doc; `whyNoButton`, `pressButton`, `removeButton`.
  - `dialect/`: everything our markdown does differently from stock Tiptap (raw HTML as text, hand-written HTML comments kept byte for byte as chips, renderers, load/save normalisations, the marker swap, `markerSwap.ts`). `test/dialect.test.ts` is its contract: removing any rule fails it. Tiptap is pinned to exact versions: don't upgrade it (see Rules).
  - `block.agent` holds the page's agent settings (below).
- Suggestion mode: the agent never writes the page.
  - One exception the writer opts into, **Accept as a Button** (a task type with `reusable`, `sel` only): `▾` beside a card's Accept, a popup that says what it does, then the result goes in with the marker around it at `:btn` (record `status: button`, `button: { at }`; with `after` the marker moves onto the result). The button (`src/app/editor/taskButtons.ts`) sits on its own line above the text; a press runs it again with its own instruction (no input) and sends it back to pending, the run is told `run.button`, and `finishRun` puts a checked `replace` straight into the page (`applyRerun`, outcome `applied`, back to `:btn`), unless it is a decline or an answer, the writer changed the text during the run, or the page isn't canonical: then it waits as a normal card, and deciding it brings the button back. On hover `✎` changes its instruction (no run) and `⏱` sets a schedule (`button.every`, one of `BUTTON_EVERY`, `POST /api/pages/:id/tasks/:task/schedule`, `scheduleButton`): the server runs it, page open or not (`agent/schedules.ts`, started by `src/index.ts`, every 15 s: `pressDueButtons`, then the page's agents are started if none work), on any engine, skipping a page whose agents are off. `×` takes the button off. A chat on a task whose suggestion was decided (accepted, a button, rejected) can't replace a card: its suggestion becomes a new one at the end of the page as the page chat's do (`suggestFromTaskChat`), and a result for the old range is refused with a reason. A re-run's reply may only `replace`, non-empty, no `edits` (`checkReply` with `button`). On the card, `▾` never dead-ends: a result that can't be a button (`buttonBlocker`: it changes other blocks, deletes the text, holds requests, a code block at an end; `BUTTON_BLOCKED` says each in the writer's words) offers **Ask again as a button** (decision `asked_for_button`, record `wants_button`, the `run.as_button` prompt, `checkReply` with `asButton`), and that request's next card leads with Accept as a Button. `DocSession` keeps a decided task's state over an arriving file until its save (`held`).
  - The server acks a task when its run starts. The agent replies `<suggestion mode="at|replace|after" place="inline|blocks">md</suggestion>`, `<decline>`, or `<answer>` (a question about the text: kept as the record's `answer`, "Answered" chip, nothing put in the page); `suggest.ts` checks it (`checkReply`) and writes the record (`suggestion`, `mode`, `place`, `saw`), moving the task to `:sug` (`finishRun`). Three failed runs in a row decline it.
  - `<edit><before>blocks</before><after>md</after></edit>` changes other top-level blocks (`edits` in the record, found by `findBlocks`, applied on Accept by `decide`).
  - The page shows it as decorations (`src/app/editor/suggestions.ts`: preview, card, keys). Hovering its diff shows the card in the right margin (`sideCard.ts`; `stickyTop` keeps it in view); a click or the keys pin it until Escape or a click away.
  - The writer's decision is their own edit, sent with the next save (`PutRequest.decisions`), recorded by `applyPut`; `pruneFile` drops decided proposals after `ORPHAN_KEEP_MS`.
- Task type plugins: `src/shared/plugin.ts` is the API (`taskType`, shape point|range, title, keys, phases, `instruction` none|optional|required, `subject` text|image for a range): the browser half. The server half is `TaskTypeServer` (`src/server/taskTypes.ts`: `modes`/`places` a suggestion may take, `tools` the replies it takes, `prompt`, `check`, `finish`, `instructions` its built-in `type.<type>` text; a task type without one gets `defaultServer`), in `src/plugins/<taskType>/server.ts`, registered by `src/plugins/server.ts` (server only; never import it from `src/plugins/index.ts`, which the browser loads). `suggest.ts` keeps what every task type shares (the envelope, the checks, the record) and asks the task type for the rest. Built-ins in `src/plugins/<taskType>/` (`gen` a point at the caret, `sel` a range over text with an optional instruction, `img` a range over one selected image with a required one, all three on `Mod-.`: a key picks by what it acts on, `targetOf`), registered by `src/plugins/index.ts`, their `prompt.md` embedded by their `server.ts`. A comment of an unregistered task type is not a marker. `test/plugins.test.ts` runs each through the full cycle.
- `src/server/`: `api.ts` + `files.ts` (REST, lock, atomic write; every write goes through `readModifyWrite`, which never overwrites an outside edit it didn't read), `project.ts` (the file dialog, the copies, Sync and Reload changes: `.solipsist/originals/` holds each file's bytes as loaded, and `restoreSource` keeps what the writer didn't change), `live.ts` (page SSE; nothing watches the pages, only the server writes them, so every write is pushed from `pageChanged`; a test that plays an outside write uses `test/outside.ts`, or `POST /api/dev/changed/:id` from another process), `agent.ts` + `agent/` (below), `log.ts` (one JSON line per core action to `SOLIPSIST_LOG`, default `DOCS_DIR/.solipsist/server.log`, off under `bun test`), `tui.ts` (terminal view of the agents, `renderDashboard` pure; `SOLIPSIST_TUI=0` for plain output). `support.ts`: the honour-system ask to buy a licence (days with a save counted in `support.dir`, shown by `SupportNudge` when a page opens; hidden while `BUY_URL` is empty). `index.ts` stops every page's agents on SIGINT/SIGTERM (acks reset) and logs unhandled errors instead of dying. One live tab per page (a second gets 409; the agent stream joins the page's own).
- Page review (`src/server/review/`, `POST /api/pages/:id/review`): the page goes to an agent whose only tool is `comment`, so a review can't change a word of it. Candidates go `propose → filter → curate → allocate → place` (only `propose` calls a model; `curate.ts` is the seam for a second one) and land as margin comments (`Margin.tsx`, `CommentModal.tsx`). Reviewers are registered in `reviewers.ts`, each with its `review.<id>` prompt; settings `review.*`.
- `src/app/`:
  - `doc/session.ts`: `DocSession`, the client brain (save, receive, merge). Its states are the pure `sessionMachine.ts` (`step(state, event)` → state and effects; `test/session-machine.test.ts` tables every pair): change a transition there and in that table, never with a flag in `DocSession`.
  - `editor/`: Tiptap extensions (vim, new-block line, fresh flash, `markerCommands.ts` keys from the plugins, `imageTargets.ts` the image a key would act on and the hint over it, `instructionInput.ts`, `pointView.ts`/`rangeLoaders.ts` loaders, `suggestions.ts`).
  - `pages/`: `Sheet.tsx` is the page; `Frame.tsx` (top bar, banners), `Margin.tsx` (comments), `StatusBar.tsx`, `DebugPanel.tsx` (agent stream), `ModelPicker.tsx` (`ModelSelect`, `ModelMenu`), `ChatModal.tsx` (+ presentational `ChatView`), `AgentFeed.tsx` + `NoteIcon.tsx` (margin pills), `EngineIcon.tsx`, `SetupDialog.tsx` (the file picker), `SyncDialog.tsx` (Sync, Reload changes, `useSync`), `ConnectModel.tsx`.
  - Design system: `design/index.html`; tokens in `tokens.css`, CSS by surface (`chrome.css`, `page.css`, `margin.css`, `chat.css`). New UI uses its tokens and components, no raw colour (`test/tokens.test.ts`).
- `FEATURES.html`: every part of the UI, once (name, where, use, handlers, a picture), generated by `scripts/features/`: pictures are the app's own components rendered with sample data and the real editor in each state in a fake DOM, styled by the app's CSS; only the words are written (`catalog.tsx`).

## Agent

- **Settings per page**, in the file (`block.agent`: `on: false` when off, `model` as `engine:model`, e.g. `pi:openrouter/~deepseek/deepseek-flash-latest`; only non-defaults written, default Pi), via `agent/settings.ts` (`readSettings`, `writeSettings`, `onSettings`). `GET /api/pages/:id/agent` (SSE) starts the page's agents only when on (off: it holds, says `on: false` in its hello, closes when they're turned on so the tab's next stream starts them). `POST` `{ model?, on? }` writes them (a model change applies after the current run; `on: false` stops the agents); `…/agent/stop` = `on: false`. The writer's switch for it is in the agent panel (`DebugPanel`), beside the model picker. `?model=` only starts a page with no model of its own (tests; the page doesn't send it). A model whose engine can't run now is the default until it can.
- **An agent keeps its engine** (record: `agent: { engine, model, session }`): card Chat and Ask again go to the recorded one; only when it can't run does the page's engine start a fresh agent. The page-wide chat (`chat/page.ts`) opens on the page's model, with a picker in its header that saves the choice (and starts a new chat). It outlives its window like a placeholder's agent: closing it leaves a reply going, opening it joins it (`history` with `busy`); idle and unwatched it snoozes after `AGENT_WAIT_MS`; its conversation is recorded in `block.agent.chat` and resumed on the next open; New chat (`DELETE …/chat/page`) forgets it. It has the reply tools: a `suggest` call becomes a suggestion at the end of the page (`suggestOnPage`), checked during the reply. `start`/`wait`/`snooze` events and the hello's `engines` say whose agent a placeholder has (`EngineIcon`: Pi's mark on the pill, debug panel, chat button).
- **The model picker** (`src/app/pages/ModelPicker.tsx`: `ModelSelect` holds the state, `ModelMenu` is the open list): a shortlist at a glance and a search over every model the engines can run. `GET /api/agent/models` is `{ models, catalog }` (`warmEngines` first); the picker reads it the first time it is opened, since the catalog is hundreds of models and the page's hello carries the shortlist only. `agent.preferred_models` (choices, any engine) pins models to the top and gives `defaultChoice` its first runnable one. `parseChoice` takes `engine:model` only; `engineKnows` also takes a model the engine would run but doesn't list (one searched out of its catalog); `engineOffers` is strict, for where the writer picks one (`POST …/agent`).
- **Engines** are plugins (`agent/engine.ts` is the API: start, run one prompt, report steps, close; registered in `agent/engines/index.ts`, Pi the only real one). `AGENT_CMD` (JSON argv) puts a test stand-in named `fake` (`engines/cmd.ts`, models `small`, `large`) first. Every engine states two things about itself: `reportsCost` (whether a run says what it cost, so the dollar limits can see it) and `confined` (whether what it runs is limited to the image folder and localhost — Pi no, since its `bash` is not sandboxed). Scheduled buttons run unwatched on any engine, confined or not. `test/engine-contract.ts` is the API's own contract: `describeEngine` runs an engine through it, and each engine's test file calls it with a fixture on a scripted model. Each run is `agent/runOnce.ts`: start or reuse the agent, send it the prompt, wait for the reply, the agent dying or `AGENT_RUN_TIMEOUT_MS`, and account for the cost; the marker bookkeeping around it (ack, `finishRun`, stale acks, the gap) belongs to whoever asked.
  - `pi` (`@earendil-works/pi-coding-agent` in-process, `SOLIPSIST_OPENROUTER_KEY` or any login Pi has saved of its own): Pi's own config as the `pi` CLI loads it in the project folder (`~/.pi/agent`, project `.pi`); tool allowlist `SOLIPSIST_PI_TOOLS` (default no MCP/codemode/tool search); a write guard (`engines/guard.ts`) limits `write`/`edit` to the image folder (Bash isn't confined). A permission prompt can't be answered headless: refused, reported as an `error` step. Pi gets reply tools (`replyTools.ts`: `suggest`, `answer`, `decline`; `AgentEngine.replyTools`); each call is checked during the run (`RunOptions.check`, `checkRunReply`) so a bad one is fixed in the same turn, a good one ends the run as `RunResult.reply`; the envelope stays the fallback. Pi tests use the `faux` provider and a scratch `PI_CODING_AGENT_DIR`, never `~/.pi`.
    - **Its models are the writer's own**: `warm()` reads Pi's catalog from disk (`getAvailableSnapshot`, `allowModelNetwork: false`, so it is as fresh as their last `pi` refresh) and keeps it; `catalog()` is all of it, `models()` the shortlist (`pi.models`, with Pi's own `defaultModel` first), `unavailable()` is null once Pi has a key, a login of its own (`piAuthSaved`) or any model it can run. A choice is `<provider>/<model>` (`piModelFor`).
- **The loop** (`agent/pageAgents.ts`, for every engine): a `PageAgents` per page, started by the stream (`agentStream`) and working on when the tab closes; a tab that opens joins it and is told what is in flight. It stops when no tab is open and nothing is left, or on `…/stop`. It doesn't poll: it sleeps until nudged (`pageChanged(id)` in `runtime.ts`, said by `writePage`; a run ending, a snooze, a tab or chat leaving, a model change) or until a time it needs (the page settled, a held task's gap), and looks at least every `LOOK_AT_LEAST_MS` (5 s) in case a signal is missed.
  - `agent/page.ts` is what it reads of the page and each run's prompt; `test/agent-contract.test.ts` pins it with an in-memory engine. Where each task's agent stands is the pure `agent/agentMachine.ts` (`step(tasks, config, event)` → states and effects; states pending, held, acking, running, waiting, snoozed, chatting; `test/agent-machine.test.ts` tables every pair): `PageAgents` does the I/O, feeds it events and carries out its effects. Change a transition there and in that table, never with a field in `PageAgents`.
  - Each pending placeholder gets its own run on a fresh agent, up to `AGENT_CONCURRENCY` (3) per page and `AGENT_MAX_RUNS` (6) across pages (`skip` `busy`); the page's parse is cached until the file changes (`pageView`); runs wait until the page has settled. `AGENT_COST_LIMIT_DAY_USD` ($5) and `AGENT_COST_LIMIT_MONTH_USD` ($50; 0 = none), rebuilt from the log on first use so they span restarts, and `AGENT_COST_LIMIT_USD` (since server start) stop new runs (`agent/budget.ts`; `skip` `cost`). A dollar limit can't see an engine that reports no cost, so its runs are counted instead and bounded by `AGENT_MAX_UNMETERED_RUNS_DAY` (40; 0 = none), also rebuilt from the log (`skip` `runs`); a run the figure can't cover carries `costUnknown` on its `end` event and in the log, and the panel says "cost not known".
  - A failed run's placeholder is retried after the gap; one a run left waiting, once the body changes. A run longer than `AGENT_RUN_TIMEOUT_MS` (10 min) is stopped and counts as failed. An `:ack` no live run owns is stale and moves back to pending (`resetAcks`).
  - An engine that returns a `sessionId` keeps its conversation on disk: its agent is kept after the run, waits `AGENT_WAIT_MS` (5 min; at most `AGENT_MAX_WAITING` per page), then snoozes (closed), and an ask again continues it (`resume`). Margin pill states: clock (waiting), engine mark (working), check "Done" (kept), moon (snoozed), bubble (in chat; "Working…" while it answers there, `chat_busy`, sent by a task chat's `onBusy`); after the writer accepts the result the pill stays beside where it landed, "Accepted" (`src/app/editor/acceptedSpots.ts`, the page's session only), or beside a button "Last run <time>" (its record's `finished`; hover: the next scheduled run), still opening the chat. A button rewriting its own text gets no fade and no new-block line (`DocSession.applyBody`). `wait`/`snooze`/`chat_end` and the hello carry `finishedAt`/`finished`.
  - **Single-agent mode** (`agent.single_agent`, off): one lasting agent per page instead of one per request. Each pending placeholder is a turn of its conversation, one at a time (`concurrency` is 1), so what it read and wrote stays in context and every turn after the first gets the short `run.next` prompt (the placeholder, plus any kind it hasn't been told — not the protocol, the page or the kinds again). `solo` in `PageAgents` is the live one: it waits and snoozes like any kept agent, and `block.agent.solo` records the conversation to resume after a snooze or a restart. A chat takes it whole and no run starts while one is open (`skip` `chat`); a model change starts a fresh one; an engine without conversations falls back to an agent per run. The page chat keeps its own agent either way.
  - Processes are recorded (`agent/leftovers.ts`, a registry per docs folder in the temp dir); the server kills those a dead server left (`killLeftovers`).
- **Chat** (`ChatModal.tsx`): on a suggestion's card (`Mod-Alt-c`, vim `gc`) or the margin pill of a request an agent works on (engines with `chats`), and the page-wide one. One channel, `src/server/chat/` (`index.ts`): `/api/pages/:id/chat/:target`, `target` a task's id or `page` (`PAGE_CHAT`). The two differ only in their `ChatSource` (`source.ts`: `lend`, `giveBack`, `keepMs`, `intro`, `check`, `apply`, `forget`): a task's (`task.ts`) and the page's (`page.ts`, its own lasting agent, kept `AGENT_WAIT_MS` after the last window). `GET` (event stream) on a task borrows the agent (`takeAgent`: the waiting one, or its conversation woken from disk; during a run it only looks in, `watchRun`, and takes the agent when the run ends) and gives it back once no window is open and no reply is in flight (`giveBack`; closing the window, Escape or a click outside, leaves a reply going, and opening it again joins it). A message sent mid-reply is steered in (`AgentSession.steer`, Pi's `session.steer`: read after its current step, answered by the same reply; a steer that comes as the run ends becomes a reply of its own); an engine without `steer` shows only Stop; `POST` the same path says something, `…/stop` aborts, `DELETE` (the page's only) is New chat. A call to one of our reply tools is marked by the engine (`ChatBlock.reply`) and shown as the result it gave (`ReplyCard`, read by `readReplyCall`), not folded away as work; the log follows a streaming reply until the writer's own gesture scrolls it up. Every agent's stream (`StartOptions.onStream`, `shared/chat.ts` events), the page chat's too, goes through `agent/bus.ts`; `applyChatEvent` builds the view; a `<suggestion>` in a reply replaces the card's (`reviseSuggestion`).
- **Prompts** (`src/server/prompts.ts`): every instruction is a prompt with a built-in file in the repo, embedded in the build (`import … with { type: "text" }`; a task type's by its `server.ts`), and the writer's edit as a file of the same id in `prompts.dir` (`~/.config/solipsist/prompts`), read at each use. Never read a built-in from the working directory: a compiled binary runs anywhere. Read them through `promptText`/`renderPrompt`, never from the files or a string in code; a new one is a row in `FIXED` with its slots. The ids: `protocol`, `protocol.envelope`, `images`, `run`, `run.project`, `run.next`, `run.again`, `run.button`, `run.as_button`, `review`, `review.<reviewer>`, `chat.first`, `pi-chat.system`, `pi-chat.first`, and `type.<type>` per plugin. `GET/PUT/DELETE /api/prompts` (local requests only) feed the settings dialog (`SettingsDialog.tsx`). `agent/protocol.md` (tasks and markers, the reply tools, the rules) is the `protocol` prompt: it goes in the system prompt, added to the engine's own (`systemPrompt(engine)`, `instructions` in `agent/page.ts`); an engine without `replyTools` also gets `protocol.envelope` (the text envelope). The `images` prompt (how to draw an image) is not sent: the protocol names its file (`promptPath`, `{guide}`) and the agent reads it (`StartOptions.readable`). Each run's prompt (`promptFor` in `agent/page.ts`, the `run` prompt) carries `plugins/<type>/prompt.md` for its task type and each task type pending (as `<task-type name=… shape=…>`), the page file (absolute paths), and on an ask-again the proposal the writer turned down.
- Every SSE event carries its `run`; `start`/`end`/`wait`/`snooze`/`chat`/`chat_end`/`revised` also the `task` (id), `start` and the hello's `runs` the `taskType`; log lines name the task as `task`. The writer sees "request" for a task and "task type" for its type.

## Rules

- A key hint names the key through `keyLabel` (`src/app/keys.ts`: `Mod-Alt-y` is ⌥⌘Y on a Mac, Ctrl+Alt+Y elsewhere), never a written ⌘ or Ctrl.
- After any UI or prop change run `bun run typecheck`; the editor tests use a fake DOM and never render React pages. Render-test new components (`test/debug-panel.test.tsx` is the pattern).
- **After any UI change run `bun run features` and commit `FEATURES.html`**: a new part of the UI needs an entry in `scripts/features/catalog.tsx` (name, where, use, handlers, specimens built from the real component or the real editor via `page.ts`), and a changed one needs its picture refreshed. `test/features.test.ts` fails when a component of `src/app/pages` or `src/app/editor` isn't in the catalog (wiring that isn't a part of the UI goes in `SKIP` in `build.tsx`), a file path is stale, or a picture fails to render.
- Read settings through `config()` (`src/server/config.ts`), never `process.env` (`test/config-reads.test.ts` fails otherwise); `ENV_ONLY` lists the plain variables (`NODE_ENV`, `AGENT_CMD`, …). A new setting is a table row with its summary and purpose, then `bun scripts/config-docs.ts`.
- Edit scripts must assert their replacement matched; a silent no-op already shipped a crash.
- **A control's text, `title`, `aria-label` and class are a contract**: tests drive them and `FEATURES.html` documents them. Moving or dropping one means grepping for it and changing every test and the catalog entry in the same step — a control removed on its own leaves tests clicking nothing and a capability gone from the app without a word.
- **A test that fails now and then is a bug in the app until proven otherwise.** Reproduce it in a loop (a dozen runs), find what races, and fix the app; loosening the test hides it. Two came from state read after the next paint: a handler on `window` must read what the app knows *now* — a ref set in a layout effect — and not capture it in a `useEffect` that re-registers, which runs too late for a key pressed in the same moment.
- A page that fails to open or round-trip: copy it to `test/fixtures/` (`fixtures.test.ts` picks it up); `everything.md` is the edge-case page.
- **A test helper that runs as a process of its own imports `test/sandbox.ts` first** (`agent-server.ts`, `e2e/pi-server.ts`, `chat-harness/server.ts`): the sandbox is what blanks keys, logins and Pi's folder, and `test/setup.ts` (the preload) is only that import, so a helper started by hand, outside `bun test`, gets it too. `agent-server.ts` also refuses to start without `AGENT_CMD`. `test/sandbox.test.ts` fails on a spawned helper that doesn't. Never run a test helper by hand to time or debug it: run its test (`bun test <file>`, with `--timeout` to see durations).
- **No test reaches a real model or a real provider.** Engine tests inject a fake (Pi's `faux`, the `AGENT_CMD` stand-in in `test/cmd-engine.test.ts`); server-level tests use `AGENT_CMD`. `test/sandbox.ts` (loaded by `test/setup.ts`, the bunfig preload) is what keeps the developer out of the tests — config file, prompts, support count, Pi's folder, and every provider key blanked, since Bun loads `.env` first and a key there makes an engine ready and chosen. Add the key of any new engine there. A test that needs one sets and restores its own. Agent tests must prove no process outlives its stream. A fake replies with an envelope (`printf`, not `echo`: macOS's `sh` turns `\n` in the JSON into line breaks) and never writes the page; `Server.agentRun` in `test/sim.ts` plays a whole run without one.
- **Don't upgrade Tiptap** (`@tiptap/*`, and the ProseMirror it bundles in `@tiptap/pm`) unless that is the task you were given. It is pinned to exact versions on purpose: the markdown dialect leans on its exact behaviour, and even a patch release breaks the page round trip (3.32.0 → 3.32.3 did: list items read back as paragraphs, `everything.md` and the fuzz failed). Upgrading is a task of its own: every `@tiptap/*` package together, the `@tiptap/extension-list` patch redone or dropped (`patches/`, `patchedDependencies`: ordered-list content indent was one column short), then `test/dialect.test.ts`, `test/fixtures.test.ts` and `FUZZ_RUNS=16000 bun test test/fuzz.test.ts`. The same holds for Pi (`@earendil-works/*`, pinned for `test/engine-contract.ts`). Dependabot is off for this reason: every dependency is upgraded by hand.
- Every dependency has an open-source licence (the app is FSL-1.1-MIT; `NOTICE` lists them): no proprietary SDK.
- **Nothing private in the repo.** Plans and notes are kept outside it, and nothing here (code, comments, tests, `AGENTS.md`, `CONFIGURATION.md`, `README.md`, the generated pages) names one: say in the comment what the code does instead (`test/no-internal-docs.test.ts`). Nor a home path, an email, a real key or anything else personal: examples use `~` and fakes like `sk-or-...`. A hand-written claim in `CONFIGURATION.md` (an example, a path, a fallback) is checked against the code when the code changes: its example config must load (`--config <it> --print-config`).
- **Others may be editing the working tree while you work** (the maintainer, other agents). Re-read before editing, and don't revert changes you didn't make. Never `git stash`, `git checkout --` or otherwise roll the working tree back to test something: it takes their unsaved work with it. Stage and commit only the files you changed.
- Known gaps: two numbered lists in a row may merge; a bullet item that starts with a non-paragraph keeps `-`.
